# 磁盘分片图优化前后对照

本次实测表明：分片存储显著降低构图内存、提高小堆预算下的可处理容量，同时增加构图和邻接查询耗时。
这是用时间换内存的改造，当前结果不能用来宣称整体提速。

## 方法

- Node.js v22.15.0，macOS 27.2，arm64，物理内存 32 GiB。
- 相同 SQLite 输入副本：400,000 个事件、200,000 个独立动态绑定，各产生一条 assign 边。
- 分别启动独立 Node 进程，统一 `--max-old-space-size=512`；每种方案跑 3 次，交替执行顺序。
- 内存基线来自提交 `7a0290e` 的 A2，补齐 binding_id 查询及匹配以适配当前 v4 数据；保留原来的全量数组/Map 构图和表存储算法。
- 两者共用当前数据库 schema、索引和配置，各自使用默认输出存储策略。源数据库生成、复制和结果校验不计入构图时间。
- 逐条读取所有输出边计算 SHA-256，排除 edge ID，确保本用例中完整边集合等价。
- 峰值 RSS 使用子进程 `process.resourceUsage().maxRSS`，在构图完成时记录；JS 堆是进度钩子的采样峰值，不是连续追踪的绝对峰值。
- 邻接查询使用同一个 reader，均匀选取 100 个节点；包含首次查询，不包含 HTTP 开销。文件系统缓存未清空，不代表冷盘吞吐。

## 结果

下表取三轮中位数；查询 p95 一列为各轮 p95 的中位数。

| 指标 | 原内存构图 | 磁盘分片 |
|---|---:|---:|
| 构图耗时 | 2.053 s | 4.374 s |
| 构图阶段进程峰值 RSS | 615.3 MiB | 100.8 MiB |
| JS 堆进度采样峰值 | 327.8 MiB | 16.0 MiB |
| 单节点邻接查询中位数 | 0.0172 ms | 0.0435 ms |
| 单节点邻接查询 p95 | 0.0368 ms | 0.0973 ms |
| 完整输出边数 | 200,000 | 200,000 |
| 完整输出哈希 | 相同 | 相同 |

RSS 下降约 **83.6%**；构图耗时增加至 **2.13 倍**。
邻接查询有额外的目录定位和分片访问开销，本用例 p95 仍小于 0.1 ms。

再将两者都限制为 `--max-old-space-size=48`、使用相同 200,000 条边：

| 容量测试 | 结果 |
|---|---|
| 原内存构图 | V8 heap out of memory，进程失败 |
| 磁盘分片 | 成功，构图约 4.445 s，输出哈希与 512 MiB 测试一致 |

## 复现与原始数据

```sh
LOG_LEVEL=error node analyzer/benchmark-graph-compare.mjs 200000 3
```

脚本默认从固定提交 `7a0290e` 读取旧 A2，并应用 v4 绑定匹配的兼容补丁；
可用 `JANI_GRAPH_BASELINE_REF` 指定其他明确保留内存实现的基线提交。
所有输入副本、提取的基线模块和输出使用临时目录，运行结束删除，不修改项目数据库。

逐轮数据及实现哈希见 [graph-sharding-ab.json](benchmarks/graph-sharding-ab.json)。
基准脚本中没有测试目标业务代码的执行时间，也不包含 F1 导入、混合调用图或大量属性读写负载；
上述百分比只适用于该合成用例。此前百万边单方案容量测试见 [Disk-Sharded-Graph.md](Disk-Sharded-Graph.md)。
